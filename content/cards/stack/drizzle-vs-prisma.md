## What it is

- **Drizzle:** a TypeScript ORM and SQL query builder. The schema is TypeScript; queries read like SQL.
- **Prisma:** an ORM with its own schema language (`schema.prisma`) and a generated, typed client.

## How it models the problem

- **Drizzle:** the TS schema *is* the source of truth and types are inferred from it directly, with no codegen step. `drizzle-kit generate` diffs the schema into SQL migration files you can read and edit; `push` syncs without migrations for prototyping.
- **Prisma:** `schema.prisma` is the source of truth. `prisma generate` produces the client; `prisma migrate dev` diffs the schema into SQL migrations (using a shadow database to detect drift).

## Where it shines

- **Drizzle:** thin and predictable. You can guess the SQL from the code, it runs well on serverless and edge, and there's nothing to regenerate after a schema change.
- **Prisma:** very ergonomic relation queries (`include`, nested writes), mature tooling (Studio, migrate), and a big ecosystem and community.

## Where it bites

- **Drizzle:** younger; some things (complex relational queries, a few migration edge cases) need you to know SQL well. You own more decisions.
- **Prisma:** you have to remember to regenerate the client, the query layer is further from the SQL, and **defaults can live in the app, not the database**: `@default(uuid())` is generated by Prisma Client, so raw SQL inserts don't get it. Use `@default(dbgenerated("gen_random_uuid()"))` to push it into Postgres.

## What interviewers ask

- *Where does a UUID default live?* Drizzle `uuid().defaultRandom()` emits `DEFAULT gen_random_uuid()` in the database. Prisma `@default(uuid())` is app-side. Drizzle's `$defaultFn()` is app-side too.
- *How do you ship a breaking schema change safely?* Expand then contract: add the new column, backfill, switch reads and writes, then drop the old one in a later migration.
- *Why pick one over the other?* Tradeoff between SQL control and no codegen (Drizzle) vs ergonomics and maturity (Prisma).
